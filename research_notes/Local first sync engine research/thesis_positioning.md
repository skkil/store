# Thesis Positioning: Candidate A (presigned-upload media service) vs Candidate B (declarative local-first sync engine)

Research date: 2026-11-04. Sources tagged "[prior knowledge, not re-fetched]" are well-known references cited from memory and not re-verified this session. Check them before citing in the thesis.

## Q1. What does A claim, how novel is it against prior art, and what does it already acknowledge?

### Takeaway
A's own §0.1 calls it "a composition of established patterns ... plus one candidate new mechanism (the store-side fence)." The web search agrees. Reservation rows, S3 events, sweepers, outbox, and temp-file auto-expiry are common practice, from Reddit advice to commercial products. What is still defensible: (a) the framing that the second write comes from an untrusted client, so the best guarantee is "eventually both or neither", decided by a lease; (b) the S3 fence that blocks late writes, which depends on S3 conditional-write enforcement; (c) a careful measured comparison against the proxied baseline (B2). The novelty is narrow and mostly engineering and empirical work. It is not a new architecture.

### Cited Findings
**A's core claims (from /home/hyoungjoojin/Desktop/skkil/ARCHITECTURE.md)**
- Problem: with presigned uploads the client makes the second write (to S3), so the server can't retry it. The guarantee is "eventually both or neither, decided by a timeout" (§0.1).
- Principles P1–P10 (§2). The key ones: DB is the only source of truth for access; *lease before capability* (the DB row and its lease expiry are recorded before the URL is signed); revocation ≠ reclamation; keys are never reused; side effects go in the same transaction (outbox); fence late writes at the store.
- Two state machines, logical `media.status` and physical `media_objects.status`, each with CAS guards. One rule prevents dangling references: an object reaches `deleting` only when its media is no longer `pending`/`active` (§5).
- Six invariants (§13). I1 no dangling reference, I2 bounded revocation, I3 bounded reclamation, I4 no leak, I5 window bound under concurrent commits, I6 bounded late-write persistence. Each has a checker method.
- Evaluation design (§16): the same fault schedules run across B0 (flag + cron), B1 (mark-and-sweep), B2 (proxied upload + outbox, the textbook fix), P1 (reservation + lease + outbox + events + reconciler) and P2 (P1 + store-side fence).
- Novelty claims (§0.1): the fence object is the "candidate new" item, a store-side analogue of Seata's TCC anti-suspension fence table, built on enforced `If-None-Match`. Everything else is labelled "Direct" or "Adapted". The fence's feasibility is unverified (week-1 spike, §17 #7).
- Prior art A already acknowledges (§0.1, §26): transactional outbox, polling publisher, Try-Confirm-Cancel / Seata fence, Gray & Cheriton leases (SOSP 1989), IBM DB2 DataLinks, Epoxy (VLDB 2023), Cherry Garcia (ICDE 2015), ScalarDB, Rails `create_before_direct_upload!`, Cloudflare Images draft records, Docker Registry / Harbor mark-and-sweep, Java RMI DGC (for claims), Kubernetes finalizers and ownerReferences, Tang et al. SIGMOD 2022 (ad hoc transactions: 53 of 91 had correctness issues).
- Scope creep: v3–v6 add claims (§18), agentic workloads, governance, mTLS/SPIFFE, SDKs, and an MSA resilience plan. §18 says these don't change the thesis scope, but the document reads as a platform design more than a focused thesis.

**How common A's ideas are in practice**
- Practitioner forums describe the same building blocks: a DB row with a status before upload, a temp bucket plus promotion, S3 ObjectCreated → SNS/SQS → reconcile, cron sweeps for rowless objects, and "just ignore orphans, storage is cheap" — [r/aws 2024 thread](https://redlib.hbubli.cc/r/aws/comments/18xtlfl/ensuring_consistency_with_s3_presigned_urls_in); [r/aws Dec 2024](https://redlib.hyperreal.coffee/r/aws/comments/1hfyuh8/how_do_i_keep_my_s3_bucket_synchronized_with_my). One answer suggests starting a Step Functions workflow when the URL is created, waiting, then checking that both the row and the file exist, which is an ad hoc version of lease-then-expire — same thread.
- Uploadcare has the reserve-then-confirm-or-expire lifecycle as a product feature: files not marked "stored" are deleted after 24 hours (`UPLOADCARE_STORE=0`/`auto`) — [Uploadcare storage docs](https://uploadcare.com/docs/uploads/storage/); [Uploadcare uploading docs](https://uploadcare.com/docs/uploading-files). Transloadit documents purging temporary files — [Transloadit FAQ](https://assets.transloadit.com/docs/faq/temporary-purge-sooner/).
- tus has an "expiration" extension, and implementations run expiry sweepers. Supabase's tus store has `deleteExpired()`, which removes `.info` files and issues `AbortMultipartUpload`, plus a lifecycle rule that aborts incomplete multipart uploads after 1 day. Unfinished resumable-upload URLs expire within 24 h — [Supabase discussion #51060](https://github.com/orgs/supabase/discussions/51060). A Rust tus crate's reclaimer does lock → reload → recheck expiry → reclaim — [tus-protocol reclamation.rs](https://docs.rs/crate/tus-protocol/0.0.1/source/src/lifecycle/reclamation.rs).
- Supabase Storage keeps a `storage.objects` metadata table separate from S3 bytes. A DB restore brings back rows without bytes, so you get dangling metadata and 404s. The DB↔blob divergence that A addresses is a real, documented failure mode in a major product — [SimpleBackups](https://simplebackups.com/blog/restore-supabase-storage-objects). I found no Supabase doc describing a reconciler.
- PowerSync, a local-first sync product, ships built-in "attachments": a local-only attachments table, a queue, and a storage adapter with upload/download/delete, retried on the next sync. It is now built into the SDKs, and the old helper packages are deprecated — [PowerSync attachments docs](https://docs.powersync.com/client-sdks/advanced/attachments.md); [PowerSync blog](https://www.powersync.com/blog/building-offline-first-file-uploads-with-powersync-attachments-helper). The docs I saw do not describe referential-integrity guarantees, late-write fencing, or orphan reconciliation.

### Inferences
- Reservation + expiry + sweeper + S3 events is folklore and a commercial feature (Uploadcare, tus/Supabase). A reviewer will say "this is what everyone does." A cannot claim novelty for the lifecycle itself.
- What remains defensible: (1) a precise invariant set (I1–I6) with a checker; (2) the store-side fence, if the S3 spike works (I found no web source describing a fence placed in the object store using enforced `If-None-Match`, but that is "not found", not "proven new"); (3) the measured B0/B1/B2/P1/P2 comparison. Practitioner material makes qualitative claims only, so (3) is the strongest contribution. Few public sources quantify late-write persistence or revocation windows.
- Weaknesses: novelty is incremental; the fence depends on one vendor feature (S3 conditional-write enforcement via bucket policy), so it may not generalize to GCS, R2 or MinIO; impact is limited to teams already running presigned uploads; the v3–v6 scope dilutes the thesis.
- Strengths: highly feasible (the plan already fits Oct–Mar), very evaluable (clear invariants and baselines), and directly useful to skkil.

### Gaps
- I did not verify whether Cloudinary, Supabase or Firebase Storage use any store-side fence or document late-write (suspension) handling. One search on Supabase found nothing.
- I did not find an academic paper that targets presigned-URL dual-write consistency directly. That supports a "niche, under-studied" framing, but it is not proof of absence.
- Fence feasibility on real S3 is still unverified (A's own §17 #7).

## Q2. What recent (2024–2026) work competes with B, and which gaps could a 1-year undergrad or small team credibly attack?

### Takeaway
Industry sync engines (Zero, ElectricSQL, PowerSync, Jazz, Convex) and academic work (LoRe/ConLoc for invariants, Keyhive/KIT for access control, Cambria for schema evolution, Sal/Verus for verification) already cover each axis on its own. Two areas look open based on what I found: (a) one declarative spec that compiles to merge rules, coordination points, partial-replication filters and authz, with defined semantics for offline writes the server rejects; (b) blob-plus-structured sync with referential integrity offline. A "general reusable sync engine" competes head-on with funded companies and is not a credible undergrad deliverable. A narrow layer or semantics contribution is credible.

### Cited Findings
**Industry competitors**
- Zero (Rocicorp): official docs say it does not support offline writes. Server-side mutators can run arbitrary authz, validation and business logic; read permissions are expressive — [Zero "When to use"](https://zero.rocicorp.dev/docs/when-to-use). A 2026 third-party comparison says Zero rejects writes while disconnected — [Kanopy Labs 2026](https://kanopylabs.com/blog/tanstack-db-vs-electricsql-vs-zero-sync). A GitHub comment claims otherwise, so this is unsettled — same search.
- Local-First Conf 2025 had a talk on "General-purpose sync with IVM" (Zero's approach of incremental view maintenance for query-driven partial sync) — [LoFi Conf 2025 schedule](https://app-2025.localfirstconf.com/schedule/talks-day-1/general-purpose-sync).
- ElectricSQL handles the read path only: it streams filtered Postgres data and leaves writes to your API — [QueryPlane](https://queryplane.com/blog/electricsql-vs-powersync-vs-replicache/); [MerginIT 2025](https://merginit.com/blog/24082025-sync-engines-guide-electricsql-convex-zero). A GitHub issue claims Databricks acquired Electric in Aug 2026 and Electric Cloud is winding down. **Unverified; no primary source found.**
- PowerSync supports full offline reads and writes. Queued mutations go to a backend upload function you implement; validation and authz stay server-side and app-defined — [QueryPlane](https://queryplane.com/blog/electricsql-vs-powersync-vs-replicache/).
- Jazz v2 is described as a public alpha with a new API. I found no detail on its permission semantics — [GitHub issue](https://github.com/emrosas/perfin/issues/9) (weak source).
- Convex published an "object sync engine for local-first apps" design — [Convex Stack](https://stack.convex.dev/object-sync-engine).
- Smashing Magazine (May 2026) covers local-first architecture, a sign of mainstream interest — [Smashing](https://www.smashingmagazine.com/2026/05/architecture-local-first-web-development/).

**Academic competitors and gaps**
- *Invariants / mixed consistency:* LoRe is a programming model and compiler that checks developer-specified safety invariants and inserts coordination only where needed — [LoRe arXiv 2304.07133](https://arxiv.org/pdf/2304.07133). ConLoc, "Consistent Local-First Software: Enforcing Safety and Invariants" (IEEE TSE, published Jan 2025) — [ACM DL](https://dl.acm.org/doi/10.1109/TSE.2024.3477723); follow-up "Safe Mixed-Consistency Local-First Software with Invariants" at SE 2026 — [GI DL](https://dl.gi.de/items/c32fef84-33dc-4862-8cfe-559db2047e08). **This is the closest prior art to the "declarative semantics + invariant-aware mixed consistency" idea. B must position against it.** As far as I could tell, LoRe/ConLoc target a language-level model (Scala/reactives), not a Postgres-backed sync engine with partial replication, authz, or blobs.
- *Access control:* Keyhive (Ink & Switch) proposes "convergent capabilities" so access control travels with the data and works offline — [Keyhive notebook](https://www.inkandswitch.com/keyhive/notebook/01/); [FOSDEM Automerge + Keyhive](https://fosdem.org/schedule/event/BZ9CAE-automerge). Jacob, Stuber, Hartenstein (KIT), arXiv 2604.23560 (Apr 2026), say Matrix and Keyhive "rely on an informal specification and an unverified reference implementation". They verify a simplified group-membership RDT in Rust/Verus and leave real-world scale to future work — [arXiv 2604.23560](https://arxiv.org/abs/2604.23560). Kleppmann gave the PaPoC 2025 keynote "Byzantine Eventual Consistency and Local-First Access Control" — [PaPoC 2025 program](https://papoc-workshop.github.io/2025/program.html). The work I found targets P2P/Byzantine settings. Server-authoritative sync engines (the enterprise case: offline write → server rejects on reconnect → what does the client see?) appear less formalized. In Zero and PowerSync this is left to arbitrary app code (see above).
- *PaPoC 2026 (27 Apr 2026)* program: Sal (multi-modal RDT verification, Sivaramakrishnan's group), a keynote on push-button RDT verification, ERA (duelling admins in group-management CRDTs), ConflictSync (bandwidth-efficient divergent-state sync, Baquero), AegisSheet (compositional spreadsheet CRDT), Semantic Conflict Model, Bounding Byzantine impact. **No paper on schema evolution or blobs** — [PaPoC 2026 program](https://papoc-workshop.github.io/2026/program.html).
- *Schema evolution:* Cambria (Ink & Switch; PaPoC 2021) uses bidirectional edit lenses. The TypeScript implementation is experimental, and lens storage and selection were left open — [Ink & Switch Cambria](https://www.inkandswitch.com/project/cambria/); [MIT DSpace](https://dspace.mit.edu/handle/1721.1/145983); [Fission discussion](https://talk.fission.codes/t/notes-on-data-interoperability-and-schemas/1591). I found no 2025–2026 follow-up.
- *Testing:* a Jepsen test suite for causal consistency and strong convergence in local-first/CRDT-style sync, using Elle with "strong-session-consistent-view". The README names no specific product tested and reports no real bugs — [jepsen-causal-consistency](https://www.github.com/nurturenature/jepsen-causal-consistency). bones-sim is a Rust DST harness for CRDT convergence, commutativity, idempotence and causal consistency, with drops, reorders, partitions, clock drift and reproducible seeds — [bones-sim](https://docs.rs/crate/bones-sim/latest). Convex engineers said they were building DST for their commit protocol, inspired by Dropbox's sync-engine DST — [Convex Discord](https://discord-questions.convex.dev/m/1325282887846727734). **I found no published DST- or Jepsen-style study of a full sync engine that includes partial sync, authz rejection and blobs.**

### Inferences
- **Credible gaps for 1 year (ranked):**
  1. *Rejection semantics for offline writes under server authz and invariants.* Define what happens when a buffered offline write is later rejected by authz, an invariant, or a revoked capability: rollback, compensation, causal cascade to dependent writes, and how it shows in the UI. Specify it formally (TLA+/Quint/P) and implement it. Zero sidesteps this by not supporting offline writes. PowerSync leaves it to app code. Keyhive and KIT target P2P/BFT, not server-authoritative systems.
  2. *Blob + structured referential integrity offline.* A row referencing a blob created offline: upload ordering, dangling references when the upload fails or authz rejects it, and GC. PowerSync attachments covers the mechanics but documents no invariants. A's lease/claim/fence machinery (§18 claims) maps onto this directly. PaPoC 2026 had nothing on blobs.
  3. *Declarative spec → compiled artifacts* (CRDT type choice, coordination points, sync filters, authz rules), positioned as "ConLoc/LoRe ideas applied to a Postgres-backed sync engine with partial replication." This carries the highest novelty risk, because ConLoc owns the invariant-to-coordination idea.
  4. *DST/Jepsen harness for sync engines* as the main contribution: a reusable checker applied to 2–3 existing engines (e.g., PowerSync, Electric + write path, Automerge-repo). This is highly evaluable and could find real bugs, but it is less "build an engine". Its novelty depends on what it finds.
- Schema evolution is open but hard to evaluate convincingly in 1 year. It works better as a limitation or future work.
- B's weaknesses: crowded, fast-moving field with funded competitors; "reusable sync engine" is huge; CRDT text collaboration is solved (Yjs, Automerge, Loro), so it adds integration work but no novelty; the risk of an unfinished system is high; and the thesis can turn into a framework demo without a sharp research question.

### Gaps
- I could not find PaPoC 2026 or Local-First Conf 2026 abstracts in detail. ConLoc's exact DSL and backend scope are inferred from the abstract.
- I did not verify Jazz's or Triplit's permission and offline-rejection models, or Ditto, Couchbase Lite or Realm (enterprise offline-sync incumbents). These should be checked before claiming gap (1).
- I did not verify the Electric/Databricks acquisition claim.

## Q3. How should B be evaluated?

### Takeaway
Use three layers. (1) Micro-benchmarks against standard CRDT traces. (2) Sync-protocol metrics under network emulation: latency, bandwidth, time to convergence, offline-queue replay. (3) Correctness under fault injection, using a deterministic simulator plus a Jepsen/Elle-style history checker with the invariant oracle defined by the spec. Layer 3 is where an undergrad thesis can stand out.

### Cited Findings
- History checking: Elle-based checker configs for causal consistency and convergence in local-first sync exist and can be reused — [jepsen-causal-consistency](https://www.github.com/nurturenature/jepsen-causal-consistency). The Elle paper (Kingsbury & Alvaro, VLDB 2021) — [arXiv 2003.10554](https://arxiv.org/abs/2003.10554) [prior knowledge, not re-fetched].
- DST oracle design for CRDTs (convergence, commutativity, idempotence, causal consistency) with partitions, reorder and clock drift, plus seed replay — [bones-sim](https://docs.rs/crate/bones-sim/latest). Simulators catch bugs Jepsen misses, but they cannot find bugs outside what the model expresses, so pair them with real-cluster tests — [sled simulation](https://sled.rs/simulation); [DST blog](https://mohakchugh.is-a.dev/blog/deterministic-simulation-testing).
- Industry precedent for DST of sync engines: Dropbox's sync engine, and Convex's commit protocol — [Convex Discord](https://discord-questions.convex.dev/m/1325282887846727734). FoundationDB simulation testing — [FDB testing](https://apple.github.io/foundationdb/testing.html) [prior knowledge, not re-fetched]. TigerBeetle VOPR [prior knowledge, not re-fetched]. Antithesis offers a commercial deterministic hypervisor [prior knowledge, not re-fetched].
- CRDT benchmarks: dmonad/crdt-benchmarks (Yjs/Automerge/etc.: doc size, parse time, memory, update size) — [GitHub](https://github.com/dmonad/crdt-benchmarks) [prior knowledge, not re-fetched]. Editing traces including the automerge-paper trace and those used by Eg-walker (Gentle & Kleppmann, EuroSys 2025) — [josephg/editing-traces](https://github.com/josephg/editing-traces), [Eg-walker arXiv 2409.14252](https://arxiv.org/abs/2409.14252) [prior knowledge, not re-fetched]. "B4" is commonly the Automerge-paper trace label in crdt-benchmarks [prior knowledge; verify].
- Bandwidth-efficient divergent-state sync is an active metric area (ConflictSync, PaPoC 2026) — [PaPoC 2026 program](https://papoc-workshop.github.io/2026/program.html).
- Formal verification options: TLA+/Quint/P for protocol models. Verus for verified Rust authz logic — [arXiv 2604.23560](https://arxiv.org/abs/2604.23560). Sal for multi-modal RDT verification — [PaPoC 2026](https://papoc-workshop.github.io/2026/program.html).

### Inferences
Proposed methodology:
- **Correctness (primary):** write the declarative spec's invariants as oracles: convergence, no dangling blob reference, rejected writes fully compensated, no unauthorized data on the client after revocation within a bound (the analogue of A's I2). Run a seeded DST across N clients × offline periods × partitions × server crashes × authz revocations mid-offline. Report violations per 10^6 schedules, with and without each mechanism (ablation). Cross-check selected runs with real processes plus Toxiproxy and Elle.
- **Performance:** time to convergence after reconnect versus offline duration and queue length; bytes per sync (full versus delta versus filtered partial); p50/p99 local write latency; server CPU per client; initial sync time for partial replicas. Use crdt-benchmarks or editing traces for any text/CRDT component and compare against raw Yjs/Automerge to show the overhead the layer adds.
- **Baselines:** (a) hand-written app logic on PowerSync or Electric (the status quo); (b) a "no offline writes" baseline (Zero-style); (c) the proposed spec-driven engine. Measure correctness bugs found and lines of app code needed for the same app (developer-effort proxy).
- **Model checking:** a TLA+/Quint model of the rejection and blob-reference protocol, checked for small configs, with trace validation against implementation logs.
- **Case studies:** 2 apps (e.g., skkil clipboard + hiking app with photos) to show expressiveness.

### Gaps
- I did not re-fetch crdt-benchmarks, Eg-walker, FDB, TigerBeetle or Antithesis pages this session, so the exact trace names (B4 etc.) should be verified.
- I found no standard benchmark for partial replication, authz or offline rejection. The thesis would have to define one, which is itself a possible contribution.

## Q4. What are the concrete thesis-scope options, and how feasible is each?

### Takeaway
The best balance of novelty, feasibility and evaluability is **Option 3 (hybrid)**: a sync layer focused on *offline writes that reference blobs, under server authz*, reusing A as the blob subsystem, with DST and a formal model as evidence. Pure A is the safest. A full general sync engine is the riskiest.

### Cited Findings
- Supporting evidence for the options is in Q1–Q3. Key anchors: A's existing invariant/baseline harness (ARCHITECTURE.md §13, §16); PowerSync attachments lacking documented integrity invariants ([docs](https://docs.powersync.com/client-sdks/advanced/attachments.md)); Zero not supporting offline writes ([docs](https://zero.rocicorp.dev/docs/when-to-use)); ConLoc/LoRe owning invariant-to-coordination ([TSE 2025](https://dl.acm.org/doi/10.1109/TSE.2024.3477723)); no blob or schema-evolution papers at PaPoC 2026 ([program](https://papoc-workshop.github.io/2026/program.html)); KIT stating that access-control verification at real scale is open ([arXiv 2604.23560](https://arxiv.org/abs/2604.23560)).

- Recommended framing for Option 3: *"Referential integrity and rejection semantics for offline-first apps with large objects."* State 3–4 invariants in A's style: no dangling blob reference after convergence; a rejected offline write leaves no orphan blob and no dependent row; data revoked from a partial replica is unreadable within a bound; convergence holds under partition and crash. Show that the baselines violate them under DST and that the proposed design does not, then report the cost in bandwidth and latency.
- Honest risks for B overall: competitors are funded and moving (Zero, PowerSync, Jazz v2); a 1-year undergrad cannot match them on a general engine, so the thesis must be a semantics-and-verification contribution plus a working prototype, not a product.
