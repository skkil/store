# Merkle / content-addressed structures and data versioning for a generic offline-cloud sync SDK (as of 2026-11-04)

Tags: [F] = fetched/searched this session (2026-11-04); [M] = from model memory, not re-verified this session (URL given is the expected primary source). The SDK in question is the design in `reports/Local first sync engine research.md`: local SQLite <-> Postgres, a **server-ordered per-user mutation log** (`server_version`), a SHA-256 CAS blob store plus media service, two-way FS mounts, and opt-in E2EE in which clients run a deterministic validator over the ciphertext log.

## Q1. Structures: what each does, why, and its tradeoffs

### Takeaway
Merkle structures fall into three families. (a) **Hash-linked histories** (Git commits, Automerge change DAG, Eg-walker event graph, Hypercore, Merkle-CRDT clocks) give integrity, causality and fork detection. (b) **Deterministic ("history-independent") Merkle indexes over current state** (Prolly trees, MSTs, Merkle tries) give O(diff) comparison, structural sharing and cheap snapshots. (c) **Reconciliation protocols over sets** (Git negotiation, Bloom-filter sync, range-based set reconciliation) find what the other side is missing when there is no total order. A server-ordered log already has a total order, so a plain seq cursor is the optimal anti-entropy for the main path. Merkle structures earn their place for integrity, verification, blob-set repair and branch diffs, not for the main pull.

### Cited Findings

**Git object model and negotiation**
- [M] Git stores blobs, trees, commits and tags as objects addressed by their hash (SHA-1, with SHA-256 repos optional). Commits point to a root tree and to parent commits, so any commit hash authenticates the whole history behind it. Fetch negotiation is a `want`/`have` exchange: the client advertises commit hashes it has, walking back from its tips, until the server ACKs common ancestors. The server then builds a **packfile** containing only the missing objects, delta-compressed against objects the client already has. Protocol v2 added `ls-refs` filtering and partial clone (`--filter=blob:none`) — [git protocol-v2 docs](https://git-scm.com/docs/protocol-v2); [pack-protocol](https://git-scm.com/docs/pack-protocol).
- [M] Implication of this design: negotiation cost grows with how far the histories diverge, and it relies on a DAG ancestry walk. That suits branching histories. It is overkill when one server defines a single total order.
- [F] A September 2026 paper by Erick Lavoie, "The Essence of Git: Concepts for P2P Replication" (arXiv 2609.13555, submitted 2026-09-11, 8 pp.), argues that Git's object model and incremental replication protocols are general enough for applications beyond VCS. It ties commit history to convergent replicated data structures and compares Git's level of abstraction with current P2P frameworks. I read only the abstract — [arXiv](https://arxiv.org/abs/2609.13555).

**Merkle DAGs / IPLD and Merkle-CRDTs**
- [M] IPLD generalises Git-style hash linking to arbitrary CBOR/JSON nodes addressed by CIDs, which are self-describing multihash and codec identifiers — [ipld.io](https://ipld.io/docs/).
- [F] "Merkle-CRDTs: Merkle-DAGs meet CRDTs" (arXiv 2004.00107, first posted 2020-03-31, revised 2020-04-27). The arXiv authors are Sanjuán, Pöyhtäri, Teixeira and Psaras; the go-ds-crdt README credits only the first three. The paper uses a Merkle-DAG as transport and persistence for CRDTs, treats the "Merkle-Clock" itself as a state-based CRDT, and gives per-object causal consistency without reliable messaging or a fixed replica set — [arXiv](https://arxiv.org/abs/2004.00107).
- [F] go-ds-crdt is a key-value datastore implemented as an add-wins OR-set, where priority comes from the height of the DAG node. It runs in production as the state-sync layer of IPFS Cluster — [GitHub](https://www.github.com/ipfs/go-ds-crdt).
- [M] Known tradeoff: a Merkle-Clock DAG grows without bound. A new replica has to walk the DAG back from the heads, which needs many round trips when the DAG is deep. Pruning or compaction is not built in.

**Prolly trees (Noms -> Dolt)**
- [M] A Prolly ("probabilistic B-") tree is a B-tree whose node boundaries come from content-defined chunking: a rolling hash or a key hash crossing a threshold. Its shape therefore depends only on the contents, not on insertion order (history independence). Equal subtrees have equal hashes, which gives structural sharing between versions and diffs proportional to the size of the change. Dolt replaced Noms's original chunker with a key-based boundary function to cut write amplification — [Dolt: Prolly trees](https://www.dolthub.com/blog/2024-03-03-prolly-trees/); [Noms](https://github.com/attic-labs/noms).
- [F] Dolt merges like Git, with a three-way merge across base, ours and theirs. The diff between the ancestor and each branch defines that side's changes. This "works great" when the two branches touch independent parts of the database. Merges happen at **cell level**. Conflicts are stored by primary key in a **separate prolly tree** next to the table, and each conflict keeps all three versions of the row — [DoltHub 2020-07-15](https://www.dolthub.com/blog/2020-07-15-three-way-merge); [DoltHub 2024-06-19](https://www.dolthub.com/blog/2024-06-19-threeway-merge/). Schema conflicts are a separate class — [DoltHub 2023-05-01](https://www.dolthub.com/blog/2023-05-01-schema-conflicts/).
- [F] The independent `prollytree` Rust/Python crate documents the same idea. A diff prunes every subtree whose hash is equal on both sides — [docs](https://zhangfengcdt.github.io/prollytree/theory/versioning/).
- [M] Cost: every write rewrites about log_B(n) nodes, so it pays O(depth) hashing and node writes plus garbage. Dolt needs explicit GC (`dolt gc`) to reclaim chunks that are no longer reachable — [Dolt docs](https://docs.dolthub.com/).

**Merkle Search Trees (Auvolat & Taïani 2019; AT Protocol)**
- [M] Auvolat & Taïani, "Merkle Search Trees: Efficient State-Based CRDTs in Open Networks", SRDS 2019. The level of each key comes from the leading zeros of its hash. That makes the tree shape deterministic, so the structure itself is a state-based CRDT (a set or map) that peers reconcile by recursive hash comparison — [HAL](https://inria.hal.science/hal-02303490).
- [F] Each AT Protocol (Bluesky) account repository is an MST that maps `<collection>/<rkey>` to record CIDs. Depth is the number of leading zero bits of SHA-256(key) divided by 2, so the fanout is **4**. Tree shape depends only on the current contents. A commit is `{did, version:3, data:<MST root CID>, rev:<TID, monotonic>, prev, sig}`, signed over DRISL-CBOR with the DID's signing key. `prev` is required in v3 but "almost always null", which means **atproto keeps no history chain**: the signed root covers current state only — [atproto repository spec](https://atproto.com/specs/repository).
- [F] atproto sync: a diff is a CAR slice with the new commit, new MST nodes and created or updated records. Deletions do **not** leave tombstones. The firehose verifies a diff by inverting the operations and checking that the result reproduces the previous root. The spec warns that CAR imports can resurrect deleted records — [atproto spec](https://atproto.com/specs/repository).
- [F] The snippets disagree on fanout: an indigo fork describes "fanout 16" and arroba's docs say "~32". The spec says 2 bits per level, which gives fanout 4. Trust the spec — [indigo fork](https://pkg.go.dev/gitlab.com/wysteriary/indigo/atproto/repo/mst); [arroba](https://arroba.readthedocs.io/en/stable/_modules/arroba/mst.html).

**Range-based set reconciliation (RBSR): Meyer, Negentropy, Willow, iroh-docs**
- [F] Aljoscha Meyer, "Range-Based Set Reconciliation and Authenticated Set Representations", arXiv 2212.13567 (v1 2022-12-27, v2 2023-02-07). It reconciles two sets by recursively partitioning a sorted key space and comparing fingerprints of each range. The paper analyses which fingerprint schemes are secure, cuts local computation by a log factor, and shows that secure **associative** fingerprints yield authenticated tree structures that need no deterministic balancing scheme — [arXiv](https://arxiv.org/abs/2212.13567v1).
- [F] Negentropy (hoytech) implements RBSR with three range modes: Skip, Fingerprint and IdList. It never sends empty fingerprints; it sends an empty IdList instead. Items are 32-byte IDs, usually the hash of the record. Nostr standardises it as **NIP-77**, and it has been explored for Waku Sync — [GitHub](https://github.com/hoytech/negentropy).
- [F] Other implementations: iroh-docs `ranger` (Rust) and Deno `range_reconcile` — [docs.rs](https://docs.rs/crate/iroh-docs/0.99.0/source/src/ranger.rs). A 2026 arXiv paper covers storage designs ("range-summarizable order-statistics stores") for RBSR — [arXiv 2603.19820](https://arxiv.org/pdf/2603.19820).
- [F] Willow runs 3D RBSR over subspace, path and time, using fingerprints of 3D ranges. Willow deletes by **prefix pruning**: a newer entry at a path prefix overwrites every older entry below it, so one tombstone deletes a whole subtree. The Rust WGPS sync is reported to be in production, and the Go port is pre-MVP — [jzhao notes](https://jzhao.xyz/thoughts/Willow-Protocol); [willow-data-model](https://docs.rs/crate/willow-data-model/0.7.0/source/src/groupings/mod.rs); [willow-go](https://pkg.go.dev/github.com/Deln0r/willow-go). These are secondary sources; the full spec is at willowprotocol.org and I did not fetch it.
- [M] Why RBSR matters: it needs no shared history and no total order, takes O(d log n) communication for d differences, and works over any sorted set. Examples are a set of blob hashes, or of (id, version) pairs.

**Merkle tries over timestamps (Actual Budget)**
- [F] Actual Budget logs field-level LWW messages with HLC timestamps (`messages_crdt`, so the data is stored twice). It keeps a Merkle tree **keyed by timestamp** over the messages each client has applied. Clients compare roots, then walk down to find *how far back in time* they diverge, and request every message since that point. If the hashes can never match, the user is told to reset sync — [James Long, "Using CRDTs in the Wild"](https://jlongster.com/using-crdts-in-the-wild). The loot-core detail comes from a third-party write-up — [Geneva](https://jamesgeneva-site.pages.dev/posts/read-actual-budget-local-first-sync). This is 2019-era material, so the current code may differ.
- Why Actual needs it: its server is a relay with no total order, so a cursor alone cannot find the gap. The Merkle trie stands in for a seq cursor. The SDK *has* a server seq, so it does not need this for the main path.

**BLAKE3 / Bao verified streaming (Iroh)**
- [F] iroh-blobs names a blob by its 32-byte BLAKE3 root and uses the BLAKE3 tree for **incremental verification while streaming**. The outboard (tree hashes) is stored separately from the data file, and it only goes down to **16 KiB chunk groups** instead of 1 KiB to keep the outboard small. A Bao issue cites 64 KiB, which is probably out of date. Range requests must align to chunk groups. Iroh moved from BLAKE3's undocumented `guts` API to a new `hazmat` API — [iroh blobs docs](https://iroh.computer/docs/protocols/blobs); [hazmat blog](https://iroh.computer/blog/blake3-hazmat-api); [blob store design](https://iroh.computer/blog/blob-store-design-challenges).
- Relevance: the SDK's CAS is SHA-256, which can only verify a blob once the whole file has arrived. BLAKE3/Bao allows resumable, range-verified downloads (lazy originals, streaming video) and verification against an untrusted server or peer.

**Hash-linked op logs (Automerge, Eg-walker, Hypercore)**
- [F] Automerge keeps the full edit history as a Git-like, hash-linked commit graph. The classic sync protocol sends a **Bloom filter** summarising the commits a peer knows (10 bits and 7 hashes per item, about 1% false positives) and repairs misses with extra rounds — [beelay/sedimentree.md](https://github.com/automerge/beelay/blob/main/docs/sedimentree.md); [Automerge bloom.rs](https://docs.rs/crate/automerge/latest/source/src/sync/bloom.rs).
- [F] **Attack:** with adversarially chosen commit hashes, the Bloom sync degrades until round trips scale with the number of commits — [hoytech/automerge-poison](https://github.com/hoytech/automerge-poison).
- [F] **Sedimentree** (Automerge/Beelay design document, undated, © 2026 footer, status unclear) addresses three problems: the current protocol needs the whole commit graph in memory, takes an unbounded number of rounds, and an **E2EE server cannot compact ciphertext** for new peers. Sedimentree linearises commits by a reverse-DFS from the heads and cuts that order into "strata" at commits whose hash has enough leading or trailing zeros (the document itself says both). Higher strata cover lower ones. Peers exchange summaries of stratum boundaries and fetch or recurse into the ranges they lack. Because chunk boundaries are content-defined, peers with the same history agree on chunks, so the encrypted chunks deduplicate. Open questions it lists: when plaintext peers should upload compacted snapshots, and how a server chooses among them — [GitHub](https://github.com/automerge/beelay/blob/main/docs/sedimentree.md).
- [F] Kleppmann's alternative Automerge sync proposal drops Bloom filters for Merkle trees over a linear order that is the same on every replica — [Notion](https://martinkl.notion.site/Alternative-sync-protocol-for-Automerge-documents-51270ac6f6e14c819b5118a9df0b897f).
- [M] Eg-walker (Gentle & Kleppmann, EuroSys 2025) stores a plain event graph of text operations with parent pointers. That graph can be hash-identified, and CRDT state is rebuilt only while merging divergent ranges. It is efficient at merging long-lived branches — [arXiv 2409.14252](https://arxiv.org/abs/2409.14252).
- [M] Hypercore (Holepunch/Dat) is a single-writer append-only log. A flat-tree Merkle tree over the entries has its root **signed by the writer's key**, so readers can verify any entry or range sparsely. A writer who signs two conflicting forks is detectable, and Hypercore 10 added explicit truncation and "fork id" support — [Hypercore docs](https://docs.pears.com/building-blocks/hypercore).

**Irmin, Fireproof**
- [M] Irmin (OCaml, Tarides) is a Git-format store whose values are **mergeable data types**. Each type supplies a three-way `merge(base, a, b)` function, and the store provides branches and merges. Tezos uses it, with irmin-pack as its storage — [Irmin](https://irmin.org/).
- [M] Fireproof (JS) is a document DB built on a Merkle-CRDT clock (Pail, an IPLD prolly-tree-like index) with encrypted CAR-file blocks. Any storage backend works, because the data is content-addressed and encrypted on the client — [Fireproof docs](https://use-fireproof.com/docs/architecture).

**Homomorphic set hashes (relevant cheap alternative)**
- [M] WhatsApp's E2EE "app state sync" (multi-device contacts and settings) uses **LtHash**, a lattice-based homomorphic set hash. Clients can then check that the server-delivered set of encrypted mutations equals the state they expect, with each mutation updating the hash in O(1) and no tree needed — [WhatsApp Security Whitepaper](https://www.whatsapp.com/security/WhatsApp-Security-Whitepaper.pdf); [Facebook LtHash paper, Lewi et al. 2019](https://eprint.iacr.org/2019/227).

### Inferences
- The SDK has two "spaces". Rows have one server total order, where a cursor is optimal and Merkle is only for verification. The **blob CAS is an unordered hash set**, which is the textbook case for RBSR (Negentropy-style): "which of my blob hashes does the server or peer lack?" after an outage, a restore (the Supabase rows-without-bytes failure mode cited in the main report) or a GC sweep.
- History-independent indexes (Prolly, MST) and homomorphic set hashes both give a **state digest** that a client can recompute and compare. That is exactly what a deterministic-replay validator needs to show "my replay equals your replay" in E2EE mode.
- Sedimentree is the closest prior art for "sync of a hash-linked log through a ciphertext-only server". The SDK's server-ordered log avoids most of Sedimentree's problems, because the order is given rather than derived, but it inherits the **snapshot/compaction problem**: the E2EE server cannot compact.

## Q2. Versioning products: how others do history, branching and time travel

### Takeaway
Products split into three camps. **Storage-level copy-on-write branching** (Neon, Xata, lakeFS, Nessie) is cheap and coarse, works at database or table granularity, and merges poorly or not at all. **Merkle-structured data versioning** (Dolt, TerminusDB, Irmin) does cell-level diff and three-way merge but owns the storage engine. **Document/app-level history** (Google Docs, Notion, Figma, Patchwork/Automerge) is fine-grained and user-facing, and is built from an op log plus snapshots. A sync SDK that already has an ordered mutation log is closest to the third camp. It can get time travel and branches as *log* features without Merkle storage.

### Cited Findings

**Ink & Switch Patchwork (2024 notebook; lab active 2026)**
- [F] Patchwork entries, Feb–Jul 2024: "universal version control" built on Automerge. Every change is auto-saved, history is queryable dynamically with a few groupings (by author, by time), and manual milestones are optional. **Edit groups** let contributors group and explain their edits retroactively, and reviewers revert rather than approve — [Patchwork notebook](https://www.inkandswitch.com/patchwork/notebook/2024-version-control/).
- [F] **Simple branching**: branches are fast to create, switch, merge and delete. Edits go to main by default, branches can be created retroactively, **branches only come from and merge back to main**, and merged branches are deleted. AI bots propose changes on branches, and AI-generated change summaries were the most effective diff aid tried. Branching ported easily to a tldraw diagram editor and a spreadsheet, but **diffs and comments needed per-domain work**; spreadsheets, for example, must separate manual edits from formula recalculation — [same](https://www.inkandswitch.com/patchwork/notebook/2024-version-control/).
- [F] Automerge fits this well because it never deletes data, keeps per-character IDs (precise diffs) and merges concurrent branches. The team reported trouble representing changes so they could be **cherry-picked** across branches — [same](https://www.inkandswitch.com/patchwork/notebook/2024-version-control/); [search summary](https://www.inkandswitch.com/patchwork/notebook/06/).
- [F] The 2026 Patchwork notebook entries (Mar–May 2026: "Progressions", "Local-First Task Framework", "grjte's Account History", and others) list titles only. I did not read their content — [notebook](https://www.inkandswitch.com/patchwork/notebook/).
- [M] Upwelling (Ink & Switch, 2023) is a writing tool with Git-like "drafts" layered on a shared document — [Upwelling](https://www.inkandswitch.com/upwelling/).

**DB branching (copy-on-write)**
- [F] Neon: a branch is a copy-on-write clone in the pageserver; nothing is overwritten in place. Every read carries an **LSN**, and the pageserver rebuilds the page as of that LSN from a base image plus WAL, which supports time-travel queries and branching from any time or LSN within the **history-retention window**. Current docs say the default is 6 h on Free and 1 day on paid plans; older material says 7 days. Longer retention costs more storage — [Neon architecture](https://neon.com/docs/introduction/architecture-overview.md); [Neon PITR](https://neon.com/blog/point-in-time-recovery).
- [M] PlanetScale branches are mainly **schema** branches with deploy requests; data is not merged. Xata offers copy-on-write Postgres branches, mainly for dev/preview environments. None of these does row-level merges — [PlanetScale](https://planetscale.com/docs/concepts/branching); [Xata](https://xata.io/).
- [M] lakeFS gives Git semantics (branch, commit, merge) over object-store data lakes using metadata pointers, so branches are zero-copy. Project Nessie gives Git-like catalog-level branches and tags for Apache Iceberg tables, with multi-table commits. Iceberg itself offers snapshot time travel plus table-level branches and tags — [lakeFS](https://docs.lakefs.io/); [Nessie](https://projectnessie.org/); [Iceberg branching](https://iceberg.apache.org/docs/latest/branching/).
- [M] TerminusDB is a Git-for-data graph database with immutable delta layers, branches, merges and time travel — [TerminusDB](https://terminusdb.com/docs/).

**App-level history**
- [M] Google Docs keeps a revision history of every edit, grouped into named and auto versions. Notion page history is retained for a plan-dependent window (7 days on Free, longer on paid plans). Figma has version history plus **branching** for design files, with a review/merge flow on Organization/Enterprise plans. Onshape is a CAD tool whose data model is a database of immutable microversions with branches and merges, so every change is a version — [Figma branching](https://help.figma.com/hc/en-us/articles/360063144053); [Onshape](https://www.onshape.com/en/features/data-management).
- [M] Git LFS and DVC keep large files out of the Merkle history by storing a pointer file (hash plus size) in Git and the bytes in a separate content-addressed store. This is the same metadata/bytes split the SDK uses with its CAS and media service — [Git LFS](https://git-lfs.com/); [DVC](https://dvc.org/doc).

**Temporal SQL**
- [F] PostgreSQL 18 adds **temporal constraints**: `PRIMARY KEY/UNIQUE (..., valid_period WITHOUT OVERLAPS)` on a range-type column, and temporal foreign keys with `PERIOD`. This is *application/valid time* only. Core Postgres still has **no SQL:2011 system versioning** and no `FOR SYSTEM_TIME AS OF`. The third-party `periods` extension (PG 14–18) adds SYSTEM_TIME and history tables. Xata reports that PG 19 Beta 1 adds `UPDATE/DELETE ... FOR PORTION OF` (not verified against official notes) — [Neon PG18 temporal](https://neon.com/postgresql/postgresql-18/temporal-constraints); [Xata](https://xata.io/blog/postgres-as-a-temporal-db); [periods](https://github.com/ludios/periods).

### Inferences
- Patchwork's lessons carry over directly to the SDK. Branches should be cheap and unnamed, fork only from main, and be deleted after merge. Generic machinery (history, branch, merge) can live in the engine, while **diff presentation stays app-specific**, which matches the "app declares meaning" split in the main report.
- Neon shows that "time travel = base image + log replay up to position X, within a retention window" is a cost model users accept. The SDK's `server_version` is the counterpart of Neon's LSN.
- No product found does a cell-level three-way merge of *relational app data* across offline devices *and* user branches, except Dolt, and Dolt owns the storage engine.

- Product facts in this section marked [M] (PlanetScale, Xata, lakeFS, Nessie, TerminusDB, Figma, Notion retention, Onshape) were not re-verified this session. Plans and retention periods change often.
- I found no published design of Notion's or Google Docs' internal history storage.

## Q3. Implications for the SDK: what to adopt, at what cost

### Takeaway
Adopt three things. (1) A **hash-chained, server-ordered log** in both modes: a few bytes per op, it gives tamper evidence and SPORC-style fork detection in E2EE mode, and replay inputs that are provably identical. (2) **RBSR over the blob hash set** for anti-entropy and repair, while keeping seq cursors for rows. (3) **Branches and time travel as log features**: a branch is a base seq plus an overlay log, merged by re-running named mutations. Defer Prolly or MST table indexes. If a state digest is needed, use a homomorphic set hash (LtHash) per table/user. Budget for GC, retention windows and crypto-shredding from day one.

### Cited Findings
- [F] SPORC (Feldman et al., OSDI 2010): the server sees only ciphertext. Each client embeds a hash of the history it has seen in its operations, so the server can **split clients into divergent views but cannot join them again undetected**. Clients find forks by comparing (seq, history-hash) out of band, and SPORC recovers by replaying and transforming forked ops with OT. Its guarantee is fork-* (weak fork-linearizability), weaker than full fork-linearizability — [SPORC paper](https://ceres.cs.umd.edu/818/papers/sporc.pdf); [OSDI slides](https://static.usenix.org/events/osdi10/tech/slides/feldman.pdf); [arXiv 1502.04496](https://arxiv.org/pdf/1502.04496.pdf).
- [M] SUNDR (Li et al., OSDI 2004) introduced fork consistency for an untrusted file server. Certificate Transparency and Key Transparency apply the same idea with signed tree heads plus gossip — [SUNDR](https://www.usenix.org/conference/osdi-04/secure-untrusted-data-repository-sundr).
- [F] atproto signs only the current-state MST root and leaves `prev` null. A signed state root alone authenticates state, not history, so it cannot show that the server dropped or reordered intermediate ops — [atproto spec](https://atproto.com/specs/repository).
- [F] Automerge's Bloom sync can be forced into O(#commits) rounds by adversarial hashes. In an untrusted-server setting the reconciliation protocol itself is an attack surface — [automerge-poison](https://github.com/hoytech/automerge-poison).
- [F] With E2EE, the server cannot compact or snapshot. Sedimentree leaves open how plaintext clients should upload snapshots and how a server should choose among them — [sedimentree.md](https://github.com/automerge/beelay/blob/main/docs/sedimentree.md).
- [F] Crypto-shredding encrypts personal data under per-subject keys, keeps the ciphertext and its hashes in the immutable log, and destroys the key on an erasure request. Inclusion proofs keep working after shredding. Its limits: data that escaped the encryption boundary (logs, indexes, analytics) is not shredded, and the problem becomes reliable key destruction. **No court decision was found affirming that crypto-erasure satisfies GDPR Art. 17.** The sources are mostly vendor-authored — [Conduktor](https://www.conduktor.io/glossary/crypto-shredding-for-kafka); [Rosenwinkel, DEV](https://dev.to/norbertrosenwinkel/you-cant-delete-an-event-gdpr-says-you-must-crypto-shredding-is-the-truce-26ak); [Key Transparency commentary](https://social.trom.tf/display/642c5671-e73ea96456148ab8-03c1b729).
- [F] atproto has no tombstones on deletion, and CAR imports can resurrect deleted records. A content-addressed system needs an explicit deletion semantics, or deleted data comes back through replication — [atproto spec](https://atproto.com/specs/repository). Willow's prefix pruning is a designed answer to this (one tombstone deletes a subtree) — [jzhao notes](https://jzhao.xyz/thoughts/Willow-Protocol).
- [F] Neon caps history with a retention window, and storage cost grows with the window — [Neon](https://neon.com/docs/introduction/architecture-overview.md).
- [M] Hashing content without a key leaks equality. An E2EE server holding plain SHA-256 of blobs can confirm guesses ("does this user have file X?") and link the same file across users. Convergent encryption trades that leak for cross-user dedup — [Douceur et al. 2002, "Reclaiming space from duplicate files"](https://www.microsoft.com/en-us/research/publication/reclaiming-space-from-duplicate-files-in-a-serverless-distributed-file-system/). The main report already chose keyed HMAC IDs for clips; blobs need the same choice.

### Inferences (design recommendations)
1. **Hash-chained log in both modes: adopt.** Per user, define `h_n = H(h_{n-1} || server_version_n || device_id || H(ciphertext_or_payload_n))`. In E2EE mode the server places mutations, anyone can compute the chain, and each client checks that (a) its own submitted mutations appear, (b) every head it saw earlier is a prefix of the current chain, and (c) devices exchange `(n, h_n)` whenever they can (LAN/QR pairing, or piggybacked inside encrypted mutations: "device D saw head h at n"). Piggybacking turns SPORC's out-of-band fork comparison into in-band, encrypted gossip that the server cannot forge. This **makes deterministic replay meaningful**: every honest validator replays the *same* hash-identified prefix, so "identical decisions" can be checked by comparing the chain head and a state digest. In standard mode, have the server sign (or publish) checkpoint heads, which yields auditability at near-zero cost. Cost: 32 bytes and one hash per op. Fork *recovery* is the hard part. SPORC uses OT. The SDK would treat the fork point as a branch point and rebase the minority fork's named mutations, reusing the branch-merge machinery below.
2. **Anti-entropy.** Keep `server_version` cursors for rows; they are optimal with a total order. Use **RBSR (Negentropy-style) over the blob hash set** between client and media service, and in future between devices on a LAN, to repair after restores, cursor loss or GC. Use a **per-scope state digest** (LtHash, or MST root) at checkpoints to detect silent divergence (bugs, partial replication errors, the PowerSync-CVE class) without a full resync. Actual Budget's Merkle trie solves a problem the SDK does not have, a missing total order, so do not copy it.
3. **Prolly/MST table index: defer, keep it optional.** It pays off only for O(diff) diffs between arbitrary snapshots or branches of large tables, and for verifiable partial reads. Cost: log(n) hashing and node writes on every write in SQLite, plus GC. Diffs between log positions can be computed from the log itself (the rows touched between seq a and b), which covers the common case. Revisit if the SDK grows to multi-GB per-user datasets or P2P without a server.
4. **Branches and time travel, cheaply.** Time travel to seq N means taking the nearest snapshot at or below N and replaying the log to N (Neon's model). A branch is `{branch_id, base_seq, overlay mutation log}` stored locally, and optionally synced as its own log stream. Merge re-runs the branch's **named mutations** against main's head through the same validator; this is a rebase. Intent-carrying mutations make that more robust than a state-diff three-way merge, though cell-level conflicts on fields typed LWW still need a policy. Follow Patchwork: unnamed branches that fork only from main and are deleted on merge, with generic history in the engine and diff UI in the app. Blobs are immutable in the CAS, so branches never copy bytes, only claims, and branch claims must enter the GC lease logic. Server-side, Postgres 18 temporal constraints cover valid-time app semantics, but system-time history must come from the SDK's own log or the `periods` extension.
5. **Costs to specify.**
   - (a) **Log growth.** Use per-scope retention windows plus snapshots. In E2EE mode, clients produce encrypted snapshots, and the server keeps one per window keyed by `(seq, h_seq)`, so a snapshot is bound to the chain; this answers Sedimentree's "which snapshot" question.
   - (b) **GC.** Blob reachability must include branches, retained history and offline leases.
   - (c) **Erasure.** Use per-user (or per-subject or per-record-group) data keys in both modes, so erasure is key destruction while the hash chain stays verifiable over the leftover ciphertext. Plaintext copies in Postgres (standard mode), search indexes and logs must be deleted for real. Mark the legal sufficiency of crypto-erasure as unsettled.
   - (d) **Content-hash privacy.** Use keyed hashes for blob IDs visible to an E2EE server, giving up cross-user dedup.
   - (e) **Reconciliation DoS.** Prefer RBSR with bounded rounds over Bloom-filter sync on untrusted links.
6. **Thesis angle.** The novelty does not lie in "Merkle sync", which is crowded (atproto, Negentropy, Willow, Iroh, Automerge). It lies in combining **fork-detectable server ordering with deterministic client-side validation and blob-claim GC under E2EE**. This is SPORC-like integrity for a *validated relational op log with blobs*. I found no system that combines these.

### Gaps
- No source found that evaluates hash-chained, server-ordered logs combined with client-side deterministic validation (SPORC used OT on text, not invariant-checked relational mutations). This looks like a gap, but I did not search exhaustively.
- I did not verify LtHash's exact use in WhatsApp's current whitepaper or its security assumptions this session ([M]).
- I found no measured overhead numbers for prolly/MST indexes on SQLite at the SDK's scale.
- The GDPR legal status of crypto-shredding is not settled by any court decision I found.
