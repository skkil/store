# High-frequency collaborative apps (Notion-like): architectures and SDK requirements (as of 2026-11-04)

Tags: [F] = fetched/searched this session; [M] = from model memory (training cutoff mid-2026), not re-verified. Treat [M] claims as leads to verify.

## Q1. Notion: data model, transactions, real-time, sharding, offline

### Takeaway
Notion is a "record mode" system at its core: blocks are rows, edits are client-generated operation batches (transactions) sent to `/saveTransactions` and validated server-side against before/after state, and fan-out is a version-notification bus (MessageStore) followed by pull. Offline mode (announced Aug 2025, engineering post Dec 2025) did not replace that. Notion added a guaranteed SQLite store with a pinning model, push channels per page, and migrated offline pages to a CRDT model for rich-text conflict resolution. In effect it bolted a "live document mode" onto a record engine, per page.

### Cited Findings
- [F] Block = UUIDv4 id, `type`, `properties` (e.g., `title`, `checked`), `content` (ordered array of child IDs), `parent` (upward pointer). Changing type only changes `type`; properties are preserved. — [Notion: data model](https://www.notion.com/blog/data-model-behind-notion)
- [F] Permissions inherit from ancestors via the `parent` pointer, not `content` arrays, because a block may be referenced from multiple arrays (ambiguity) and walking down is inefficient. Parent and content pointers "mirror" each other except edge cases "being cleaned up". — same
- [F] Each UI action = operations that create or update a single record. Operations are batched into a **transaction** that the server commits or rejects atomically. The client generates IDs, applies locally, writes to an in-memory store plus RecordCache (SQLite/IndexedDB LRU), and queues the transaction in a **TransactionQueue** until it is acknowledged. — same
- [F] Server `/saveTransactions` flow: load the involved records and parents ("before"), apply ops to a copy ("after"), validate permissions and coherency using both, commit, ack (the client then sends the next queued transaction, so it is **serial per client**), then async work: version-history snapshots, search indexing, MessageStore notify. — same
- [F] Real-time: a long-lived WebSocket to **MessageStore**, subscribed per rendered record. MessageStore pushes *new version numbers*, not data. The client compares with its cached version and calls `syncRecordValues` to pull. Reads use `loadPageChunk` (a server-side tree walk) on a cache miss. — same
- [F] Sharding: partitioned by **workspace ID**. 2021: 32 physical DBs × 15 logical schemas = 480 logical shards. 2023 re-shard: 96 DBs × 5 schemas each (still 480). Done with Postgres logical replication (3 publications per old DB), dropping indexes during the copy (3 days to 12 h), splitting PgBouncer into 4 groups of 24, dark-read validation, a 4-step per-DB failover, and reverse replication for rollback. Post dated 2023-07-17. — [Notion: The Great Re-shard](https://www.notion.com/blog/the-great-re-shard)
- [F] Data lake (2024-07-01): blocks went from more than 20B rows (early 2021) to more than 200B, hundreds of TB compressed, doubling every 6 to 12 months. **"90% of Notion upserts are updates."** Debezium CDC (one connector per PG host), then Kafka (one topic per table across 480 shards), then Hudi (COPY_ON_WRITE, UPSERT, bloom index) to S3. Lag is minutes for most tables and up to about 2 h for blocks. Originally Fivetran with 480 hourly connectors into Snowflake. — [Notion: data lake](https://www.notion.com/blog/building-and-scaling-notions-data-lake)
- [F] Offline mode (post by Raymond Xu, 2025-12-11; feature announced Aug 2025): SQLite went from a best-effort cache to a guaranteed store. Pages toggled "Available offline" are **migrated to a CRDT data model**, and a page with missing data is never shown offline. The post cites "rich-text conflict resolution" as a problem solved. — [Notion: How we made Notion available offline](https://www.notion.com/blog/how-we-made-notion-available-offline)
- [F] Pinning model: an `offline_page` table (the set) plus an `offline_action` table, with one row per reason (`origin_page_id`, `from_page_id`, `impacted_page_id`, `type` such as `toggled` or `favorite`). Invariant: a page stays offline while at least one action references it. Reasons include toggle, favorite, auto-download of recent pages, and inheritance (for example, up to 50 rows of a database's current view). — same
- [F] Polling per offline page was rejected as unscalable. Instead the server emits a message on a **per-page channel** whenever it applies a batch of updates, and clients subscribe to their offline pages. On reconnect the client compares a per-page `lastDownloadedTimestamp` with the server's `lastUpdatedTime`, then reconciles the offline forest with minimal inserts and deletes. — same
- [F] The post does **not** detail the CRDT implementation or block-level versus rich-text conflict rules. — same

### Inferences
- Notion's pre-offline design leaned on "server validates before/after state". A CRDT page cannot be validated that way per keystroke, so validation probably moved to the page/ACL level for CRDT pages. This is unverified.
- The `offline_action` reason table is a reusable SDK primitive: **subscription/pin reasons with reference counting** for partial replication ("why is this entity on device?"). It maps directly to a generic SDK's scope/subscription API.
- Version-notify followed by a pull (MessageStore) is cheap fan-out for record mode. CRDT mode instead needs to push the update bytes, or the pull cost multiplies per keystroke.
- A 90% update share means write amplification matters even in record mode. Storing CRDT blobs naively as row updates would make it worse (see Q4).

### Gaps
- No primary source on how Notion stores CRDT pages server-side (blob vs ops), whether non-offline pages also use CRDTs now, or block-move conflict semantics.
- No public numbers on Notion transaction rate per user or batching interval. [M] Recollection: the Notion client coalesces typing into transactions (debounced). Not verified.

## Q2. Other systems: Google Docs, Figma, Linear, tldraw, Excalidraw, Miro, Coda, Quip, Craft, AFFiNE, AppFlowy, Anytype, Liveblocks, PartyKit/DO, Y-Sweet, Hocuspocus, Automerge-repo

### Takeaway
Two dominant patterns. (a) **One authoritative actor/process per document** holding the doc in memory, used by Figma, tldraw sync, PartyKit/Durable Objects, Y-Sweet, Hocuspocus, Liveblocks, and Google Docs. (b) **One global or per-workspace ordered log** for records, used by Linear (lastSyncId), Notion, Zero, and Replicache. Products that need both run the two side by side: Figma syncs comments and teams from Postgres separately from the multiplayer document server.

### Cited Findings
- **Figma** [F]: one multiplayer server *process per document* over WebSockets. The server is the authority and its arrival order makes per-(object, property) LWW timestamp-free. Values are atomic. Clients apply locally and discard incoming server values that conflict with unacked local edits (no flicker). Object IDs embed a client ID (offline creation). Existence is an LWW boolean. A tree is a child→parent link plus **fractional index stored as one atomic property**. The server rejects parent cycles, and clients temporarily hide cyclic objects. Offline reconnect means downloading a fresh doc, reapplying local edits, and reconnecting. Undo principle: undo-many, copy, redo-to-present leaves the doc unchanged. Deleted object data lives only in the deleter's undo buffer. "Inspired by CRDTs" but not one. OT was rejected for non-text. Comments, users, teams, and projects are synced separately from Postgres. — [Figma: multiplayer](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)
- **Figma LiveGraph** [M]: a separate real-time subscription layer over Postgres (WAL tailing, query invalidation) for non-document data such as comments and file lists. It was rewritten around 2024 ("LiveGraph 100x"). Figma also wrote about a write-ahead journal for multiplayer persistence (around 2023–24) so the in-memory doc isn't lost between checkpoints. Not re-fetched. — [Figma blog](https://www.figma.com/blog/)
- **Linear** [F]: client transactions go to the server, which broadcasts **delta packets** (to the originator too). Each sync action carries a sync ID, and a single global `lastSyncId` counter (shared across workspaces, with permission filtering) detects gaps. The local DB updates only when the matching delta arrives. Deltas may differ from the transaction because of server side effects (e.g., history). Storage is IndexedDB. Community characterization: LWW with no conflict detection. This is a reverse-engineered source, not official. — [reverse-linear-sync-engine](https://github.com/wzhudev/reverse-linear-sync-engine), [HN](https://hn.svelte.dev/item/44123131)
- **Linear rich text** [M]: issue descriptions and Docs reportedly use ProseMirror plus Yjs, separate from the model sync. A search this session found **no confirming source**. — (unverified)
- **tldraw sync** [F]: exactly one `TLSocketRoom` per room globally, required for correctness. On Cloudflare that means one Durable Object per room, with state in DO SQLite (`SQLiteSyncStorage`, also on Node via better-sqlite3/node:sqlite) and assets in R2. Schema validation and migrations run in the room so mixed client versions can collaborate. Hibernation snapshots idle sessions after about 5 s. A separate object-store lane handles comments, threads, and reactions with per-session `objectAccess` read/write. Client and server versions must match ("please refresh"). Offline is not covered. — [tldraw sync docs](https://tldraw.dev/docs/sync)
- **Y-Sweet** [F]: Rust Yjs server that persists to S3-compatible storage (or a local dir). Scales "horizontally with a session backend model". Per-document client tokens are minted by the app backend via `getOrCreateDocAndToken(docId)` after the app checks access. MIT. — [GitHub y-sweet](https://github.com/jamsocket/y-sweet). [F] Jamsocket announced it was joining Modal on **2025-07-10**. Products "continue to operate normally while core functionality is migrated", so the long-term future of hosted Y-Sweet and Plane is unclear. — [Modal blog](https://modal.com/blog/jamsocket-is-joining-modal)
- **Hocuspocus** [F]: the Database extension uses `fetch(name)` → Uint8Array and `store(name, state)` → upsert **full state blob**. `fetch` must return exactly what `store` saved, because creating a fresh Ydoc duplicates content. — [Hocuspocus database ext](https://tiptap.dev/docs/hocuspocus/server/extensions/database). [M] The server debounces store (defaults around 2 s debounce, 10 s maxDebounce). Not re-verified.
- **Automerge-repo** [F]: storage keys `[docId, "incremental", hash]` per change. Periodic compaction writes `[docId, "snapshot", heads]` and deletes only the incrementals it loaded. Snapshots keyed by heads make concurrent compaction by multiple processes safe without locks, and on load everything is merged. Adapters need only KV with range ops. — [Automerge storage](https://automerge.org/docs/reference/under-the-hood/storage/), [Repo](https://automerge.org/docs/reference/repositories/)
- **AFFiNE/BlockSuite** [F, low confidence]: snapshot plus incremental `updates` tables in Postgres (BYTEA, keyed by workspace and doc), squashed periodically, with server merging via Rust yrs. Sources are third-party mintlify pages, schema "simplified". — [mintlify AFFiNE local-first](https://mintlify.com/toeverything/AFFiNE/features/local-first), [CRDT storage](https://mintlify.com/toeverything/AFFiNE/api/storage/crdt). [M] BlockSuite models each block as a Y.Map inside one Y.Doc per page, with subdocs per page in a workspace.
- **Liveblocks** [F]: two doc models in one room. Storage (LiveObject/LiveList/LiveMap plus **LiveText**) shares one undo history and one version restore. Yjs `Y.Doc` sits in the same room with its own lifecycle. LiveText is limited to 2 MB per instance, and Yjs is recommended for long docs. Offline is "experimental" and only in Yjs mode. — [Liveblocks text editing](https://liveblocks.io/docs/products/sync/text-editing.md)
- **Google Docs** [M]: OT with a central server, derived from Jupiter (Nichols et al., 1995). The client has at most one outstanding change batch in flight plus a pending buffer, and the server transforms against concurrent ops and assigns revision numbers. Offline is limited (cached via extension or service worker). — [Jupiter paper (UIST'95)](https://dl.acm.org/doi/10.1145/215585.215706)
- **Excalidraw** [M]: per-element `version` / `versionNonce` reconciliation (higher version wins, nonce tiebreak), fractional indices added around 2024, E2EE rooms via a relay server, and Firebase for persistence. — [Excalidraw blog](https://blog.excalidraw.com/)
- **PartyKit / Durable Objects** [M]: the canonical "actor per document" pattern. A single-threaded object addressed by name holds the WebSocket fan-out and state with transactional SQLite storage. PartyKit was acquired by Cloudflare (2024). — [Cloudflare DO docs](https://developers.cloudflare.com/durable-objects/)
- **AppFlowy** [M]: Rust `collab` crate over yrs, with one collab object per document/database/folder, a Postgres-backed AppFlowy-Cloud that stores collab blobs plus updates, and snapshots for history. **Anytype** [M]: any-sync, a DAG of encrypted change "trees" per object, P2P plus sync nodes. **Craft, Coda, Quip, Miro**: not researched this session (no claims).
- **Jazz** [F]: current docs (2026) describe Jazz as a "**local-first relational database**" with tables (`s.table`), row-level permissions, `db.insert`/`db.subscribe(...).where(...)`, and offline writes. "Classic Jazz" (CoValues: CoMap, CoList, CoText, Groups) docs are now separate, so Jazz appears to have pivoted from CoValue graphs toward a relational API. — [Jazz docs](https://jazz.tools/docs)

### Inferences
- Every high-frequency doc system puts **an in-memory authoritative copy per doc** in one place: process, DO, or room. Postgres is the checkpoint, not the hot path. A generic SDK's live mode needs a routing layer (docId → actor) plus a checkpoint/journal policy.
- Figma's design shows **per-property LWW + server order + fractional index + cycle rejection** is enough for trees and canvas without CRDTs. That is effectively the user's record mode with per-field merge rules. Only text needs a sequence CRDT.
- Durable-but-separate lanes (comments, ACL, metadata) are universal: Figma uses Postgres/LiveGraph, tldraw an object-store lane, Liveblocks Comments. This supports routing comments and mentions through record mode, not inside the CRDT doc.

### Gaps
- No fetched source on Figma LiveGraph internals, Google Docs batching intervals, Miro, Coda, Quip, or Craft.
- AFFiNE schema not verified against its Prisma source.

## Q3–Q4. Concrete requirements: update rate, batching, presence, actor vs log, fan-out, write amplification, permissions, undo, comments, moves, rich text, large docs, cold start, history

### Takeaway
Keystroke-rate updates (5–10/s per typist) must never become one Postgres row commit plus one global-log entry each. Coalesce on the client (around 100 ms debounce), sequence in a per-doc actor, append small updates, and compact into snapshots. Presence is never persisted. Permissions are per document (a token at connect), not per update.

### Cited Findings
- **Batching** [F]: Y-Electric recommends `debounceMs` (e.g., 100) so each keystroke doesn't PUT — [electric-yjs skill](https://tanstack.com/intent/registry/%40electric-sql__y-electric/electric-yjs). PowerSync batches update inserts through an `insert_document_updates` Postgres function — [PowerSync blog](https://powersync.com/blog/postgres-and-yjs-crdt-collaborative-text-editing-using-powersync.md). Notion acks transactions serially per client — [Notion data model](https://www.notion.com/blog/data-model-behind-notion).
- **Write amplification and storage shape** [F]: PowerSync stores **one row per Yjs update** (`document_updates(id, document_id, update_data BYTEA)`) explicitly because rewriting large blobs in place is inefficient, and a periodic edge function merges updates. Limitation: no BYTEA sync, so base64 in sync rules. Published 2024-01-16, updated 2025-11-17 — [PowerSync](https://powersync.com/blog/postgres-and-yjs-crdt-collaborative-text-editing-using-powersync.md). Electric uses a `ydoc_update(id, room, update BYTEA)` table streamed as a shape filtered by room. The README examples are inconsistent across versions (`row.op` vs `row.update`) — [y-electric npm](https://npmjs.com/package/@electric-sql/y-electric), [README 0.1.53](https://unpkg.com/@electric-sql/y-electric@0.1.53/README.md). Hocuspocus does a debounced full-blob upsert — [Hocuspocus](https://tiptap.dev/docs/hocuspocus/server/extensions/database). Automerge uses incremental chunks plus heads-keyed snapshots — [Automerge storage](https://automerge.org/docs/reference/under-the-hood/storage/).
- **Fan-out** [F]: Notion uses version-notify then pull (record), plus per-page channels for offline pages — [Notion offline](https://www.notion.com/blog/how-we-made-notion-available-offline). Linear broadcasts delta packets with a global sync ID — [reverse-linear](https://github.com/wzhudev/reverse-linear-sync-engine). Figma and tldraw broadcast within the doc process — [Figma](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/), [tldraw](https://tldraw.dev/docs/sync).
- **Permissions** [F]: Y-Sweet uses per-doc tokens minted after an app ACL check — [y-sweet](https://github.com/jamsocket/y-sweet). tldraw has per-session read/write `objectAccess` for the comments lane — [tldraw](https://tldraw.dev/docs/sync). Notion uses ancestor inheritance via `parent` — [Notion data model](https://www.notion.com/blog/data-model-behind-notion).
- **Undo** [F]: Figma uses local-only undo with an invariant (undo, copy, redo leaves the doc unchanged) — [Figma](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/). Liveblocks gives LiveText a shared undo history with the rest of Storage — [Liveblocks](https://liveblocks.io/docs/products/sync/text-editing.md). [M] Yjs `UndoManager` tracks only local origins (per-user selective undo).
- **Moves** [F]: Figma's atomic (parent, fractional index) property plus server cycle rejection — [Figma](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/). Notion's parent/content dual pointers sometimes diverge ("edge cases being cleaned up") — [Notion](https://www.notion.com/blog/data-model-behind-notion).
- **Large docs and limits** [F]: LiveText 2 MB cap; Yjs for long docs — [Liveblocks](https://liveblocks.io/docs/products/sync/text-editing.md). Notion `loadPageChunk` walks worst-case many DB round trips — [Notion](https://www.notion.com/blog/data-model-behind-notion).
- **Mixed versions** [F]: tldraw runs schema migrations in the room. Server back-compat is not guaranteed — [tldraw](https://tldraw.dev/docs/sync).

### Inferences (SDK requirements)
1. **Client coalescing**: live mode buffers local CRDT updates and flushes every 50–200 ms or on idle/blur (merge with `Y.mergeUpdates`). Record mode coalesces same-field edits in the outbox before send (last value wins locally).
2. **Ephemeral lane**: presence, cursors, and selection go over the same socket but are never logged, never in Postgres, and TTL'd (Yjs awareness model). Expose it as `doc.presence`, separate from durable state.
3. **Per-doc sequencing for live mode**: route by docId to a single actor (DO, sticky process). Do **not** push every CRDT update through the global server-ordered mutation log. Instead write one record-mode mutation such as "doc X advanced to version v / heads h" at a coarse cadence, so record-mode subscribers (lists, search, last-edited) see it without keystroke amplification.
4. **Storage**: `doc_snapshot(doc_id, state BYTEA, heads/state_vector, seq)` plus `doc_update(doc_id, seq, update BYTEA, actor, ts)`. Compact when update count or bytes exceed a threshold. Make compaction idempotent and concurrency-safe the Automerge way (key by heads, delete only what was loaded). Keep old snapshots for history and version restore.
5. **Projection to relational columns**: derive `title`, plain text, mentions, and links from the CRDT doc in the actor on checkpoint, then write them as normal record-mode fields (read-only to clients). This gives search, permissions, and data-lake visibility (Notion-style CDC) without parsing blobs downstream.
6. **Permissions**: authorize at subscribe/connect (doc-scoped token derived from the record-mode ACL row or ancestor). Revocation must kick live sockets. Per-update checks are limited to read-only vs writer.
7. **Block trees**: keep block structure in record mode (parent + fractional index as one atomic field, server cycle check à la Figma). Put only rich text per block, or per page, in a CRDT. That is the Notion/Figma split. Alternatively, one Y.Doc per page holding all blocks (BlockSuite/AFFiNE). The tradeoff: per-page CRDT gives offline merge of moves but blocks cross-page moves and fine ACLs.
8. **Undo**: local-origin only, with an operation-inverse undo stack in record mode and a CRDT `UndoManager` in live mode, unified under one `undo()` that orders by local timestamp.
9. **Comments and mentions**: record mode rows anchored to CRDT positions (relative positions / sticky indices), with an orphan policy when the anchor text is deleted.
10. **Cold start**: serve the latest snapshot plus tail updates (or a server-side merged state) and lazy-load docs. Use pin reasons (Notion `offline_action`) to decide which docs are kept locally.
11. **Offline**: record mode replays queued mutations (Figma/Replicache-style rebase). Live mode merges the CRDT update set. Notion's lesson: pages must be fully present locally to be shown offline, which requires pinning with closure over dependencies.

### Gaps
- No measured numbers found for per-keystroke update sizes or recommended compaction thresholds across products. The 50–200 ms figure is extrapolated from Y-Electric's 100 ms example.

## Q5. Two modes under one API; which products combine them

### Takeaway
Combining "rows + server-ordered mutations" with "CRDT doc per entity" is the norm in production (Figma, Notion post-2025, Liveblocks, tldraw), but in OSS sync engines it is usually a **demo-level bolt-on**: Yjs updates stored as BYTEA rows in the row-sync pipe (PowerSync, Electric). Those designs have no actor-per-doc, so every update goes through the global replication stream, and compaction is left to the app. No surveyed engine offers both regimes as first-class, typed modes with shared ACL, scope, history, and projection. That remains a plausible novelty gap.

### Cited Findings
- [F] PowerSync + Yjs: row-per-update through normal sync rules, a "very basic" merge edge function, base64 workaround, labeled "initial" — [PowerSync](https://powersync.com/blog/postgres-and-yjs-crdt-collaborative-text-editing-using-powersync.md)
- [F] Electric + Yjs (`@electric-sql/y-electric`): a shape on `ydoc_update` filtered by room, writes to an app-defined `sendUrl`, auth via a proxy, debounce — [npm](https://npmjs.com/package/@electric-sql/y-electric), [Electric demo](https://electric.ax/sync/demos/yjs)
- [F] Zero + Yjs: no official integration found. Rocicorp's earlier Reflect had `reflect-yjs` mutators — [Reflect docs](https://reflect-docs.vercel.app/how/text)
- [F] Liveblocks: Storage (structured) plus Yjs (text) in one room with shared presence and comments. Offline is experimental — [Liveblocks](https://liveblocks.io/docs/products/sync/text-editing.md)
- [F] Jazz: now a relational local-first DB API (tables, row-level perms). The relation to classic CoValues/CoText is not established from this fetch — [Jazz docs](https://jazz.tools/docs)
- [F] Figma: doc multiplayer plus a separate Postgres-backed sync for comments and metadata — [Figma](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)
- [F] tldraw: doc room plus an object-store lane for comments, threads, and reactions — [tldraw](https://tldraw.dev/docs/sync)

### Inferences (proposed API shape)
- One schema declares field types: `scalar` (per-field merge rule: LWW/server-wins/custom), `ordered` (fractional index + parent, cycle-checked), and `crdt<'yjs'|'automerge'|'text'>`. A record with a `crdt` field implicitly owns a **live document** whose id = (table, pk, field).
- `db.query(...)` / `db.mutate.x(...)` operate in record mode. `db.doc(table, pk, field)` returns a handle with `.ydoc`/`.text`, `.presence`, `.undo`, `.status`, and lazy open/close. The handle opens a socket to the doc actor only while open. Otherwise the doc syncs as snapshot + update rows via the normal log at low priority, which is how offline catch-up works.
- Server: the mutation log stays authoritative for rows. Doc actors own `doc_update` sequencing and emit coarse "doc advanced" mutations plus projections into the log. Scope/pin rules (Notion `offline_action` style) decide which docs prefetch.
- Thesis framing: formally, the record mode is server reconciliation, live mode is an op-based CRDT, and the bridge (projection plus coarse version mutation) must preserve causal consistency between a row's scalar fields and its doc heads (e.g., a mutation conditioned on doc heads). That invariant is a testable contribution (simulation).

### Gaps
- No primary source showing anyone (Zero, PowerSync, Electric) running an actor-per-doc tier alongside the row log. Absence is from limited search, not exhaustive.
- Jazz 2 internals (whether text fields are CRDT) not determined.
- Notion's server-side storage of CRDT pages remains unpublished.
